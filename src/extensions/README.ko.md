# 네이티브 확장 호스트: 설계와 보안 계약

[English](README.md) | [한국어](README.ko.md)

이 문서는 이번 변경에서 구현하는 확장 기반과 Issue #54의 후속 Codex 계정 Pool을 구분한다. 네이티브 확장은 사용자가 별도로 설치하는 신뢰된 실행 파일이다. Rust 동적 라이브러리, 에이전트 작업자, 운영체제 샌드박스가 아니다.

## 목표와 구현 범위

확장 활성화 잠금 파일을 지정하지 않으면 기존 gateway의 기본 동작을 유지한다. 명시적인 오프라인 설치, 요청 권한 승인, 변경 불가능한 패키지 선택, 재시작 기반 활성화, 선택형 메타데이터 관측 프로세스의 수명 관리를 제공한다.

최초 실행 역할은 `observer`다. gateway가 전달하는 것은 크기가 제한된 숫자형 HTTP 결과 메타데이터다. 프롬프트, 요청·응답 본문, 인증 헤더, 계정 자격증명, 도구 결과를 전달하지 않는다. 예제 실행 파일과 합성 통합 검사는 이 역할을 검증한다. ChatGPT 로그인, 한도 조회, 계정 순환 또는 Codex Pool을 구현한 것은 아니다.

## 구조

```text
Consumer / agent
    |
    | Responses HTTP
    v
Gateway core
    |-- local authentication and request admission
    |-- route and capability checks
    |-- provider transport and SSE backpressure
    |-- cancellation, capacity and retry policy
    |
    +-- bounded observation queue
            |
            v
       Native extension supervisor
            |
            | versioned local control messages
            v
       Trusted observer executable
```

모델 요청과 응답은 기존 gateway 전송 경로에 남는다. 관측 확장은 추가 모델 프록시가 아니며 모든 SSE 조각을 받지 않는다. 관측 큐 포화나 확장 장애가 모델 요청의 재실행으로 이어져서는 안 된다.

확장 호스트가 자식 프로세스의 수명을 관리한다. 소비자 애플리케이션은 계속 도구 실행, 사용자 승인, 대화 이력과 복구를 소유한다. 확장 상태를 추가한다고 Responses 대화 저장 기능이 생기지는 않는다.

## 패키지 설치와 활성화

설치와 활성화는 별도 작업이다. 패키지 준비 과정에서는 컴파일 결과를 독립적인 패키지 파일로 복사한다. 설치 과정에서는 확장 코드를 실행하지 않고 정적 명세와 전체 파일 목록을 검사한다. 메타데이터 확인을 위해서도 실행하지 않는다. 예상하지 않은 파일, 잘못된 식별자, 안전하지 않은 경로, 심볼릭 링크와 미지원 선언을 거부한다. 컴파일러가 하드링크된 산출물을 만들었다는 이유로 설치된 패키지의 무결성 검사를 완화해서는 안 된다.

패키지 정체성에는 버전과 내용 다이제스트가 포함된다. 요청한 권한이 자동으로 승인되지는 않는다. 운영자는 지원되는 권한을 명시적으로 승인해야 한다. 활성화 잠금에는 정확한 패키지 정체성과 승인 권한을 기록하고 원자적으로 교체한다. 셸 PATH나 검토하지 않은 디렉터리에서 임의의 프로그램을 찾아 실행하지 않는다.

gateway는 `--extensions-lock`을 명시적으로 지정한 경우에만 활성화 잠금을 읽는다. 오프라인 설정·manifest 검사는 활성화 자료와 패키지를 확인하지만 확장을 실행하거나 공급자에 접속하지 않는다. 실제 서버 시작 시 선택된 실행 파일과 런타임 연결을 확인한다. 버전 변경은 계획된 중지·시작으로 적용하며, 진행 중 요청 내부에서 즉시 교체하지 않는다.

패키지 체크섬은 기대한 체크섬과 내용이 일치함을 확인한다. 배포자가 신뢰할 만한 사람인지 독립적으로 증명하지는 않는다. 최초 로컬 패키지 기능은 공개 마켓플레이스, 원격 자동 갱신기 또는 배포자 서명 검증 서비스가 아니다.

## 네이티브 코드 신뢰 모델

별도 프로세스는 주소 공간을 분리하고 자식 프로세스의 장애를 관리하기 쉽게 한다. 그러나 그것만으로 실행 파일의 사용자 파일 읽기나 네트워크 접근을 막지는 않는다. 환경변수 정리와 좁은 통신 규격은 우발적 노출을 줄이는 조치이며, 적대적인 네이티브 코드를 가두는 샌드박스가 아니다.

운영자가 신뢰한 확장만 실행한다. 역할과 권한 검사는 gateway가 제공하는 인터페이스를 제한할 뿐, 확장이 직접 수행하는 임의의 운영체제 호출을 통제하지 않는다. 신뢰하지 않는 제3자 코드 실행은 운영체제 격리 또는 WebAssembly 설계를 별도로 검토해야 한다.

셸 실행과 자격증명 상속을 피한다. 비공개 상태와 런타임 소유권은 명시적으로 선택한 저장소 안에서 관리한다. 파일·디렉터리를 보호하고 유형과 정체성을 검증한다. 가변 상태를 몰래 공유하는 대신 중복 런타임 소유를 거부한다. 확장이 보낸 문자열을 신뢰된 진단으로 기록하거나 정제하지 않은 자식 프로세스 출력을 공개하지 않는다.

최초 네이티브 런타임 계약의 지원 대상은 Linux와 macOS다. Windows에서는 확장을 사용하지 않는 기존 gateway 경로를 유지한다. 네이티브 확장 실행은 동등한 ACL·잠금·IPC를 구현했다고 주장하는 대신 명시적인 미지원 결과를 반환해야 한다.

## 통신 규격, 자원 제한과 장애 처리

버전과 크기가 제한된 초기 연결 및 관측·확인 메시지 교환을 사용한다. 알 수 없는 메시지와 잘못되거나 지나치게 큰 프레임을 거부한다. 제한 시간은 완성된 프레임 전체에 적용하며 메시지 일부만 보내는 상대도 포함한다. 제한된 큐를 사용해 응답하지 않는 확장이 HTTP 요청 경로를 막지 않도록 한다. 관측 메시지는 도구 실행, 경로 변경, 비밀 정보 획득을 요청하는 콜백이 아니다.

자식 프로세스 정리와 종료 시간을 제한한다. 장애·종료 시 런타임 소유권을 해제하고 소유한 자식 프로세스를 회수한다. 확장 장애를 이유로 모델 요청을 자동 재시작하거나, 관측 정보를 모델 작업으로 재실행하거나, 일부 응답을 다른 계정에 넘겨 이어 붙이지 않는다.

요청 인증, 전송 목적지, 지원 의미, 요청·응답 크기 제한, 취소와 전송 재시도 정책의 최종 통제권은 코어에 남는다. 모듈 설치가 리다이렉트, 환경 프록시 상속, 재시도, 대체 경로, 원격 공개 또는 조용한 요청 변형을 활성화해서는 안 된다.

## 실행 정체성과 호환성

선택형 확장 구성은 정확한 패키지 정체성·권한·설정을 별도의 확장 실행 manifest에 결합한다. 확장을 사용하지 않는 소비자는 기존 manifest·readiness 계약을 유지한다. 확장 계약을 사용하는 소비자는 작업을 시작하기 전에 지원 스키마와 선택된 실행 파일·설정 정체성을 확인해야 한다.

변하지 않는 패키지·설정 정체성과 가변 운영 상태는 다르다. 후속 토큰 세대나 한도 관측값을 패키지 업그레이드로 취급해서는 안 된다. 확장 코드, 권한 또는 정책 변경은 호스트 몰래 적용하지 않고 실행 연결과 복구 검사에 포함해야 한다.

## Codex Pool: 후속 설계이며 이번 구현 대상이 아님

Codex Pool은 관측 역할보다 넓은 별도 검토 계약이 필요하다. 편의를 위해 관측 통신 규격에 자격증명이나 모델 요청 본문을 넣어서는 안 된다.

권장 책임 분리는 다음과 같다.

| 구성요소 | 책임 |
| --- | --- |
| Gateway core | 최종 허용 판정, 승인된 목적지와 자격증명 사용, 제한된 모델 전송, 취소와 시도 횟수 관리 |
| Codex Pool module | 허가된 계정의 수명, 한도·건강 상태 근거, 계정 선택 제안과 계정 연결 상태 |
| Credential owner | 인증 권한별 단일 갱신 주체, 세대를 확인한 갱신과 삭제 |
| Consumer host | 대화 원점 결합, 승인, 도구 실행, 명시적인 복구와 문맥 이전 |

후속 Pool은 전역 활성 토큰을 바꾸는 대신 요청이 소유한 계정·자격증명 임대를 해결해야 한다. 코어는 제안된 계정이 경로, 모델, 워크스페이스와 기존 세션 연결에 맞는지 확인한다. 새 작업의 계정 선택과 이미 진행 중인 대화의 인증 원점 변경은 서로 다른 작업이다.

암호화된 reasoning과 공급자 내부 상태를 계정 사이에서 옮길 수 있다고 가정해서는 안 된다. 재시작 후 연결 정보가 없거나 만료되었다고 불투명한 이력을 다른 계정으로 조용히 보내서는 안 된다. 호스트가 적절한 연속성 전이를 승인하거나, 확인된 이식 가능 문맥으로 새 스레드를 시작해야 한다.

명시적으로 거부된 요청, 아직 전송하지 않은 요청, 전송했지만 수락 여부를 모르는 요청은 재시도 판단이 다르다. 클라이언트에 도착한 바이트가 없다는 사실은 upstream이 아무 작업도 하지 않았다는 증거가 아니다. 기존 재시도 기본값을 유지하고, Pool 장애 전환 전에 명시적인 예산과 안전한 근거를 정한다. 일부 SSE, 공개된 도구 출력, 취소와 실행 여부 불확실성을 투명한 재실행의 이유로 삼아서는 안 된다.

Pool의 계정·갱신 상태는 별도의 스키마 이행과 롤백 규칙이 필요하다. 구버전과 신버전 소유자를 같은 refresh grant에 대해 동시에 실행하지 않는다. 사용자의 일반 Codex 로그인을 자동으로 가져오거나, 실행 파일 롤백과 함께 오래된 자격증명을 복원하지 않는다.

## 확장 순서

1. 내부 역할 인터페이스를 좁게 유지하고 확장 없는 기본 동작을 보존한다.
2. 합성 자료로 설치·활성화·자식 프로세스 관리·숫자형 관측 역할을 검증한다.
3. Codex Pool 구현 전에 자격증명 소유권, Codex 전송, 한도, 세션 연결과 재시도 계약을 검토한다.
4. 접근 권한과 장애 의미가 정해진 경우에만 독립적으로 유용한 역할을 추가한다. 후속 프로토콜 어댑터에는 별도 스트리밍·취소 계약이 필요하다.
5. 실제 확장 구현으로 안정적인 경계가 확인된 뒤 공개 SDK, 서명된 배포와 WASM을 검토한다.

내부 Rust 모듈과 사용자 설치형 패키지는 다른 단위다. Cargo feature는 빌드를 제어할 수 있지만 그 자체가 설치기는 아니다. 사용자가 인증·한도·스케줄러를 각각 조립하게 만들기보다 여러 내부 모듈을 일관된 Codex Pool 패키지 하나로 배포할 수 있다.

## 검증과 배포 경계

실행 없는 오프라인 설치, 정확한 권한, 패키지 변조, 안전하지 않은 파일 객체, 중복 소유권, 잘못되거나 일부만 도착한 초기 메시지, 큐 포화, 자식 프로세스 종료, 취소와 제한 시간 내 종료를 검사한다. 관측 메시지에는 지원하는 숫자형 메타데이터만 포함되고 확장 없는 동작은 바뀌지 않는지 확인한다.

선택형 `metadata_observer` 예제와 `scripts/extension_smoke.py`는 합성 자료를 사용한다. 실제 인자는 각 스크립트의 `--help`를 확인한다. 정확한 PR head에 대해 저장소가 요구하는 포맷·Clippy·잠금 Rust 테스트·Python 테스트·공개 경계·라이선스·문서 검사를 수행한다. 모의 서버와 호스팅 CI의 성공이 실제 Codex 계정 검증이나 소비자 운영 승인을 의미하지는 않는다.

프로젝트 라이선스와 제3자 고지 요구사항은 계속 적용된다. 네이티브 프로세스 분리는 공학적 경계이며, 확장 또는 SDK의 권리·배포 조건 검토를 대체하지 않는다.
