# 구현 마일스톤과 우선순위

[English](../roadmap.md) | [한국어](roadmap.md)

이 문서는 구현 단계의 의존성과 완료 기준, 남은 수락 조건을 정의한다. 계획의 작성은 기능 구현,
구조 변경 승인, 실제 공급자 검증, 공개 릴리스 또는 소비자 운영 수락을 뜻하지 않는다.
현재 지원 범위는 [HTTP 계약](protocol.md)과 [IR 계약](ir.md)을 따른다.
GitHub의 [작업 단위](work-items.md)와 [PR·CI 절차](github-workflow.md)로 진행 상태를 추적한다.

2026-09-09 문서 검토 기준 공개 소스는 `9916c4f`다. G00–G20의 승인된
설계·구현·로컬 및 hosted 검증·PR 병합은 완료됐다. M0–M6 추적 마일스톤은
닫혔으며 M7에는 [안정판 Codex 시험 기준 교체](https://github.com/novelKR/agent-response-gateway/issues/33)가 남아 있다.
이는 합성 검증까지의 구현 상태다. 실제 공급자 qualification, 소비자 생산 운영
활성화·수락과 정식 릴리스는 별도 단계로 남아 있다. 아래 항목은 각 단계의
목적과 수락 기준을 보존하며 모든 항목을 미구현으로 뜻하지 않는다.

P0는 후속 구현을 시작하기 위한 선행 조건, P1은 다중 API와 내장 사용의 핵심,
P2는 검증한 제품의 배포 완성, P3는 별도 확장이다. 같은 우선순위에서도
아래 의존성을 따른다. 작업량 추정과 목표 날짜는 실행 계약을 고정한 뒤 정한다.

<a id="starting-point-m0--responses-transport-and-ir-foundation"></a>

## 출발점: M0 — Responses 전달과 IR 기반

이미 구현된 범위는 독립 Rust 실행 파일, 루프백 인증, 모델 별칭과 공급자 키
선택, Responses JSON/SSE 전달, 준비 통지와 종료 처리, IR v1의 요청 codec,
기능 판정, custom tool JSON bridge, 이벤트 검증과 origin binding이다.

초기 M0에서는 IR과 HTTP 변환이 분리돼 있었다. 이후 M2–M4에서 IR을
Messages·Chat Completions HTTP 경로에 연결했고, 세 경로의 실제 Codex + 합성
upstream 검증을 추가했다. 현재 범위는 [공통 지원표](conformance.md)를 따른다.
M0 자체의 완료를 이 후속 검증이나 실제 공급자 수락의 증거로 사용하지 않는다.

<a id="overall-sequence"></a>

## 전체 순서

| 우선순위 | 마일스톤 | 선행 조건 | 완료 시 주장할 수 있는 범위 |
|---|---|---|---|
| P0 | M1. 검증 기반과 Codex 실행 계약 고정 | M0 | 정확한 런타임 계약과 재현 가능한 기준 시험 |
| P0 | M2. 모델 경로·기능 프로필의 실행 연결 | M1의 계약 | 검증 범위가 명시된 경로 선택과 요청 전 기능 판정 |
| P1 | M3. 첫 변환 API의 전체 도구 왕복 | M1, M2 | 첫 API의 선언된 기능에 대한 Codex 호환성 |
| P1 | M4. 두 번째 변환 API의 전체 도구 왕복 | M3 | Responses 입력에서 세 종류 upstream API 사용 |
| P1 | M5. 소비자 내장 기동과 제한된 사용 수락 | M1, M2, M3 | 검증된 경로의 자동 기동·종료 및 제한된 내장 사용 |
| P1 | M6. 장기 실행·압축·재개 수락 | M5, 대상 경로의 M3/M4 | 해당 경로의 장기 작업과 재시작 후 연속성 |
| P2 | M7. 검증 배포물과 소비자 버전 고정 채택 | 대상 기능 검증, 배포·권리 준비 | 검증한 범위의 독립 배포와 소비자 채택 |
| P3 | X. 추가 입력 API·서비스 기능 | 핵심 경로 안정화, 별도 승인 | 별도로 정의한 확장 기능 |

M4와 M5는 M3 이후 함께 진행할 수 있다. M5는 검증된 Responses 경로에 대한
기동 골격을 M1부터 준비할 수 있지만, 변환 경로의 내장 수락은 M3를 기다린다.
배포·권리 준비는 M1부터 진행하며 완료되지 않은 외부 기여·계약·배포를 차단한다.
이 의존성은 작업 계획이며 특정 실행 방식이나 에이전트 위임을 요구하지 않는다.
후속 개발은 선행 단계의 계약·구현·모의 검증을 근거로 착수할 수 있다.
실제 공급자 qualification을 기다리는 동안 다른 어댑터를 개발할 수 있지만,
그 사실로 선행 마일스톤 전체를 완료 처리하거나 미검증 경로를 운영에 사용하지 않는다.

<a id="p0--m1--validation-foundation-and-pinned-codex-contract"></a>

## P0 / M1 — 검증 기반과 Codex 실행 계약 고정

목적은 공급자 어댑터를 구현하기 전에 실제 소비자의 요구를 관찰하고,
기존 검증을 반복할 수 있도록 만드는 것이다.

- 공개 경계 검사에서 commit/tag 이외의 로컬 ref를 처리하는 정책을 정리한다.
  지원할 ref의 검사 범위와 거부 범위를 명시하고 합성 저장소 회귀 시험을 추가한다.
  검사 통과를 위해 기존 ref를 삭제하거나 알 수 없는 ref를 묵시적으로 제외하지 않는다.
- 대상 Codex 버전, 실행 파일 해시, 제어 스키마와 최종 적용 설정을 고정한다.
  제어 스키마 고정을 모델 HTTP 호환성 검증과 구분한다.
- 실제 Codex와 합성 Responses upstream을 연결하는 시험 장치를 준비한다.
  도구 선언, custom format, namespace, 도구 결과 재입력과 종료 계약을 확인한다.
- 텍스트, 함수 도구, custom 도구, 이미지, strict 출력, 취소, 재개·압축을
  필수·선택·미지원으로 분류한다. 장기 실행의 상태 소유자와 재개 방식도 설계한다.
- 첫 변환 API는 Messages, 두 번째는 Chat Completions로 고정한다.
  각 API 안에서 실제 모델 qualification의 대상과 비용 한도는 별도로 정한다.
- 모델별 입력·출력 한도, 컨텍스트 산정 방법, 압축 여유, 재시도 책임과
  실행 예산의 소유자를 정한다. 공급자별 실제 제한값은 검증된 자료로 채운다.

완료 기준: 저장소 필수 검증과 공개 경계 검사가 통과하고, 고정된 Codex의
기준 경로에서 도구 왕복·취소·승인 거절 시험이 재현된다. 모의 upstream 결과는
실제 공급자 qualification과 구분한다. 필요한 실행 파일이 없거나 계약이
확정되지 않으면 M1은 미완료로 유지한다.

<a id="p0--m2--connect-model-routes-and-capability-profiles"></a>

## P0 / M2 — 모델 경로와 기능 프로필의 실행 연결

목적은 IR의 순수 계약을 실제 요청 처리에 연결하되 기존 원형 전달의
호환성을 의도치 않게 좁히지 않는 것이다.

- 모델 경로별 API 종류, 인증 방식, 기능 프로필 버전과 한도를 설정에 연결한다.
- 별칭을 실제 경로로 해석하고 요청 처리 중 사용할 RouteSnapshot을 고정한다.
  여러 요청에 걸친 실행 고정은 소비자와 연결하며 M5/M6에서 검증한다.
- 검증된 Responses 전달 경로와 변환 경로를 명시적으로 구분한다.
  모든 원형 전달 요청에 더 좁은 IR codec을 강제로 적용하지 않는다.
- 변환 경로에서 요구 기능을 한 번 도출하고 미지원 필수 기능을 전송 전에 거부한다.
  원형 전달 경로도 qualification 범위와 알려지지 않은 기능의 처리 정책을 명시한다.
- 출력 한도를 적용하고 M1에서 정한 입력 컨텍스트 적합성 검사와 소비자 설정을
  연결한다. 바이트 크기나 근거 없는 토큰 추정치를 정확한 컨텍스트 보장으로 표시하지 않는다.
- 기존 설정의 호환성, 마이그레이션, 기능 명세의 신뢰 주체를 확정한다.

완료 기준: 합성 공급자의 요청 횟수가 0인 상태로 기능·한도 위반이 거부되고,
허용 요청은 고정한 경로로만 전송된다. 기존 Responses 전달 회귀 시험이 통과한다.
어댑터가 없는 API는 지원으로 표시하거나 다른 API로 조용히 대체하지 않는다.

<a id="p1--m3--first-converted-apis-complete-tool-round-trip"></a>

## P1 / M3 — 첫 변환 API의 전체 도구 왕복

Messages API를 먼저 완성하고 Chat Completions는 M4에서 추가한다.
요청 변환만 끝내고 스트림과 custom 도구를 뒤로 미루지 않는다.

- 요청 codec, 인증, 비스트리밍 응답과 오류를 실제 HTTP 경로에 연결한다.
- SSE/UTF-8 framing, 공급자 이벤트 parser, Event IR 검증과 Responses encoder를 연결한다.
- 함수와 custom 도구의 이름·namespace·항목 ID·호출 ID·결과 연결을 보존한다.
- 부분 wrapper JSON의 문자열 복원과 병렬 호출을 처리한다. M1의 필수 문법을
  의미 보존하며 지원할 수 없다면 전체 도구 호환성을 완료로 표시하지 않는다.
- 필수 이미지·strict 출력·추론 옵션을 구현하고 나머지 지원 수준은 명시한다.
- 단절·출력 제한·실패·취소, 느린 소비자와 버퍼 제한을 시험한다.
- 공급자 헤더, 첫 모델 이벤트, 첫 텍스트와 종료 시점을 계측한다.
  실제 화면 표시 지연은 소비자 측 측정과 구분한다.

완료 기준: 고정 Codex에서 텍스트 → 도구 호출 → 결과 재입력 → 후속 응답이
실제로 왕복하며, custom 도구·승인 거절·취소·단절 시험이 통과한다.
합성 wire 시험과 실제 공급자 시험 결과를 별도로 기록한다. 실제 공급자 시험이
없으면 구현 및 모의 호환성 검증 완료까지만 주장하고 qualification은 미완료로 둔다.

<a id="p1--m4--second-converted-api-and-common-regression"></a>

## P1 / M4 — 두 번째 변환 API와 공통 회귀

- 나머지 API에 M3의 요청·응답·스트림·도구 왕복 범위를 구현한다.
- 공통 IR의 기능 판정과 이벤트 불변식을 재사용한다. 공급자 차이는 어댑터에 둔다.
- 실제 두 어댑터에서 확인된 공통 처리만 추출한다. 가상의 후속 공급자를 위한
  범용 프레임워크나 crate 재분리를 선행 작업으로 만들지 않는다.
- 원형 전달, 첫 어댑터, 두 번째 어댑터의 동일 의미 fixture와 실패 계약을 비교한다.

완료 기준: Responses 입력에서 세 API 경로가 각각 선언한 기능을 수행하고,
세 경로 전체 회귀와 대상 모델별 qualification 상태가 정리된다.
한 모델의 통과를 같은 공급자의 모든 모델에 일반화하지 않는다.

<a id="p1--m5--consumer-startup-and-bounded-embedded-acceptance"></a>

## P1 / M5 — 소비자 내장 기동과 제한된 사용 수락

주 구현 위치는 소비자의 런타임 관리자다. 게이트웨이에는 재사용 가능한
연결 계약만 둔다. 특정 소비자의 이름·경로·설정·운영 기록을 공개 저장소에 넣지 않는다.

- 로컬 시험용 고정 바이너리와 해시 manifest로 기동 골격을 검증한다.
  외부 배포는 M7의 대응 소스·고지·권리 조건을 충족한 뒤 수행한다.
- 전용 실행 설정, 매 기동 로컬 토큰, 준비 확인 후 Codex 시작을 연결한다.
- 공급자 키 상속 범위와 로컬 토큰의 모델·프로젝트·사용량 제한을 확정·구현한다.
  공통 HTTP 인증 확장이 필요한 부분은 별도 설계 대상으로 구분한다.
- Codex 모델 선택과 실제 gateway 경로, 최종 컨텍스트 설정을 연결한다.
- 실행 중 경로·정책 고정과 명시적 변경을 관리한다. 자동 fallback은 추가하지 않는다.
- 기동 실패, 종료 순서, 고아 프로세스, 취소, 예산 소진과 복구를 시험한다.

완료 기준: 별도 수동 설치·기동 없이 검증한 경로가 준비되고 도구·승인·취소가
동작하며 개인 설정·인증을 변경하지 않는다. 이 수락은 제한된 작업 범위다.
압축·재개가 필요한 장기 사용 수락은 M6를 통과해야 한다.

<a id="p1--m6--long-running-work-compaction-and-resume"></a>

## P1 / M6 — 장기 실행·압축·재개 수락

승인된 [상태 소유권 설계](continuity-design.md)는 gateway를 stateless HTTP
전송 계층으로 유지한다. [연속성 계약](continuity.md)은 호스트가 소유하는
Codex 이력과 비공개 저널을 검증하며, 소비자 통합은 그 영속화·승인·복구를 담당한다.

- 런타임·gateway·경로·프로필·자격 증명 세대·이력·요청 예산을 binding으로 고정한다.
- Codex의 로컬 압축과 호스트 이력 재개를 사용한다. 원격 compact와 저장된
  response 조회·삭제 및 `previous_response_id`는 gateway에서 계속 거부한다.
- 불투명 상태는 동일 origin에서만 유지한다. 모델 전환은 명시적으로 새 thread를
  만들고 이동 가능한 텍스트·완료 도구 결과 및 생략한 상태를 기록한다.
- 요청 전에 진행 중 상태를 영속화하고, 재시작 후 실제 파일·실행 경로·도구
  연결을 확인한다. 불일치한 binding과 완료 도구의 중복 실행을 거부한다.
- 처리 여부가 불명확한 실행은 불확실한 상태로 남긴다. 호스트의 명시적 검토와
  복구 확인 없이 재개하거나 자동 재시도하지 않는다.
- 호스트 제어 요청 예산과 내부 HTTP 시도·실제 과금을 구분한다. 주 전송의
  자동 재시도는 0이며 실제 공급자 비용 한도는 별도로 확정한다.

완료 기준: 대상 경로별로 도구 사용 후 재개, 압축 후 재개, 프로세스 재시작,
모델 전환, 상태 불일치와 승인 거절이 시험되고 소비자가 장기 운영을 수락한다.
M4 미완료 경로에는 이 수락을 확장하지 않는다. 저장 형식 변경 시에는 이전
버전의 읽기 가능 여부와 상태·실행 파일·설정의 복구 방법을 함께 검증한다.

<a id="parallel-preparation-and-p2--m7--distribution-rights-and-consumer-adoption"></a>

## 병행 준비와 P2 / M7 — 공개 배포·권리·소비자 채택

다음 준비는 M1부터 시작할 수 있다. 상용 계약 완성을 순수 로컬 개발의
선행 조건으로 삼지 않으며, 각 활동의 실제 권리·배포 조건을 구분한다.

- 권리자와 연락 창구, 외부 기여의 출처·재라이선스 권한·동의 기록을 확정한다.
  확정 전에는 현재 정책대로 외부 코드 기여 병합을 보류한다.
- 별도 상용 계약은 독립적으로 준비한다. 정책 문서만으로 대체 허가를 주장하지 않는다.
- 검증 커밋·도구 체계·잠금 파일·대상 플랫폼·해시를 묶는 빌드 기록을 준비한다.
- 대응 소스, 실제 의존성 고지, SBOM과 빌드 출처 증명을 생성·검증하는 절차를 준비한다.
- 공개 저장소·CI·릴리스의 실제 결과를 확인하고 소비자가 해시와 출처를 검증하도록 연결한다.
- 업데이트 실패 시 이전에 검증된 조합으로 복구한다. 상태 호환성도 함께 확인한다.

완료 기준: 배포 범위의 시험, 공개 경계·archive·패키지 포함 목록 검사,
소스·고지·출처 검증이 통과하고 소비자가 고정 버전을 검증해 채택한다.
기본 AGPL 배포와 별도 상용 허가를 구분하고 실제 배포 조건을 확인한다.

제한된 preview는 해당 기능의 M3/M4 검증과 배포 조건 충족 후 별도로 릴리스할 수 있다.
장기 실행 완료를 preview의 조건으로 강제하지 않되 압축·재개 지원을 주장하지 않는다.
최종 내장 장기 운영 릴리스는 대상 경로의 M4·M5·M6 수락과 배포 조건을 모두 요구한다.
배포 세부 절차는 [배포 문서](release.md), 책임은 [통합 경계](integration.md)를 따른다.

<a id="p3--x--separate-extensions"></a>

## P3 / X — 별도 확장

다른 클라이언트 입력 API, WebSocket, OAuth·계정 풀, 관리 UI, 공개 서비스·tenant
모드, 동일 프로세스 내장은 별도 요구와 승인을 받은 뒤 계획한다. 현재 초기 목표의
완료 조건에 넣지 않는다. 루프백 경계와 기본 무재시도·무fallback 정책을 유지한다.

<a id="change-and-verification-rules-for-every-milestone"></a>

## 각 마일스톤의 변경·검증 규칙

- 완료 상태를 구현, 모의 검증, 실제 Codex 검증, 실제 공급자 검증, 소비자 수락,
  배포 검증으로 구분한다. 해당하지 않는 단계는 이유를 명시한다.
- 구조·공개 설정·상태·인증·런타임 의존성·배포 변경은 적용 전 영향과 대안,
  호환성·비용·위험·복구·검증 계획을 구체화하고 필요한 승인을 받는다.
  이 로드맵은 그러한 변경의 일괄 적용 승인이 아니다.
- Rust 변경에는 fmt·Clippy·locked 테스트를 수행하고 변경된 기능의 지원표를 갱신한다.
  공개 경계 검사와 검사기 단위 테스트, 커밋 전 검증은 저장소 지침을 따른다.
- 기본 테스트는 합성 fixture와 모의 upstream을 사용한다. 실제 공급자 호출,
  설치·배포·공개와 소비자 활성화는 해당 행위의 승인 범위 안에서 수행한다.
- 마일스톤별로 이전 검증 바이너리·설정과 지원 계약을 복구 가능하게 유지한다.
  실패한 경로를 다른 공급자나 약한 기능으로 조용히 대체하지 않는다.
